# RuoYi 性能测试计划

## 1. 测试目标

本性能测试围绕 RuoYi 后台管理系统的核心接口和核心业务流程展开，重点验证系统在不同压力模型下的响应时间、吞吐量、错误率和稳定性。

性能测试不追求覆盖所有接口，而是覆盖高频接口、核心业务链路和高风险写入流程。接口完整功能覆盖由接口自动化测试负责，性能测试重点回答这些问题：

- 核心查询接口在单接口压力下是否稳定。
- 后台只读混合业务在高峰请求频率下能否达到目标吞吐量。
- 用户、角色权限、组织架构等写入流程在低并发下是否稳定。
- 当目标 RPS 达不到时，能否通过报告定位慢接口或容量瓶颈。

## 2. 测试范围

### 2.1 登录认证

覆盖接口：

- 获取验证码：`GET /captchaImage`
- 登录：`POST /login`

测试目的：

- 验证验证码、Redis、登录认证链路是否稳定。
- 观察登录接口在低/中并发下的响应时间和错误率。

### 2.2 核心只读接口

覆盖接口：

- 用户列表：`GET /system/user/list`
- 角色列表：`GET /system/role/list`
- 菜单列表：`GET /system/menu/list`
- 部门列表：`GET /system/dept/list`
- 岗位列表：`GET /system/post/list`

测试目的：

- 单独观察高频查询接口性能。
- 为混合业务压测提供瓶颈定位依据。

### 2.3 后台只读混合业务

覆盖业务：

- 登录准备 token。
- 按业务比例查询用户列表、用户详情、角色列表、角色详情、菜单列表、部门列表、岗位列表。

测试目的：

- 模拟后台管理员高峰期只读访问。
- 验证系统在固定 RPS、阶梯 RPS、稳定负载下的承载能力。

### 2.4 用户管理读写流程

覆盖业务：

- 登录准备 token。
- 新增用户。
- 查询用户列表。
- 查询用户详情。
- 修改用户。
- 重置密码。
- 修改用户状态。
- 删除用户。
- 查询确认删除。

测试目的：

- 验证用户生命周期读写链路在低并发下是否稳定。
- 验证唯一测试数据生成和清理能力。

### 2.5 角色菜单权限读写流程

覆盖业务：

- 登录准备 admin token。
- 新增菜单。
- 新增角色。
- 新增用户并绑定角色。
- 普通用户登录。
- 查询普通用户菜单，确认看不到新菜单。
- admin 给角色分配菜单。
- 普通用户重新登录。
- 查询普通用户菜单，确认能看到新菜单。
- 删除用户。
- 删除角色。
- 删除菜单。

测试目的：

- 验证菜单 -> 角色 -> 用户 -> 用户可见菜单的权限链路。
- 验证权限配置类写入流程的稳定性和清理能力。

### 2.6 组织架构用户关联读写流程

覆盖业务：

- 登录准备 token。
- 新增部门。
- 新增岗位。
- 新增用户并绑定部门、岗位。
- 查询用户详情，确认部门岗位绑定关系。
- 删除用户。
- 删除岗位。
- 删除部门。

测试目的：

- 验证部门 -> 岗位 -> 用户的组织关系链路。
- 验证关联数据创建、查询、删除和清理能力。

## 4. 压力模型

### 4.1 基准测试

用于观察接口在低压力下的基础响应时间。

建议参数：

| 参数 | 值 |
| --- | ---: |
| 线程数 | 1 |
| Ramp-Up | 1s |
| 循环次数 | 10 |

适用场景：

- 登录认证。
- 核心只读单接口。

### 4.2 单接口高并发测试

用于观察某个核心查询接口在并发访问下的性能表现。

建议参数：

| 参数 | 值 |
| --- | ---: |
| 线程数 | 10 / 30 / 50 |
| Ramp-Up | 10s / 30s / 50s |
| 循环次数 | 10 |

适用场景：

- 用户列表。
- 角色列表。
- 菜单列表。
- 部门列表。
- 岗位列表。

### 4.3 固定 RPS 混合业务测试

用于模拟明确的高峰请求频率。

建议业务模型：

| 接口 | 占比 | 100 RPS 下目标频率 |
| --- | ---: | ---: |
| 用户列表查询 | 30% | 30 req/s |
| 用户详情查询 | 15% | 15 req/s |
| 角色列表查询 | 20% | 20 req/s |
| 角色详情查询 | 10% | 10 req/s |
| 菜单列表查询 | 5% | 5 req/s |
| 部门列表查询 | 10% | 10 req/s |
| 岗位列表查询 | 10% | 10 req/s |

建议参数：

| 参数 | 值 |
| --- | ---: |
| 线程数 | 100 起步，不足时提高到 300 / 500 |
| Ramp-Up | 5s |
| 持续时间 | 30s |
| 目标 RPS | 100 |

### 4.4 阶梯 RPS 测试

用于寻找系统容量边界。

建议阶梯：

| 阶梯 | 目标 RPS | 持续时间 |
| --- | ---: | ---: |
| 1 | 10 | 30s |
| 2 | 30 | 30s |
| 3 | 50 | 30s |
| 4 | 100 | 30s |

观察重点：

- 实际 `Throughput/s` 是否接近目标 RPS。
- Avg、P95、P99 是否明显升高。
- 是否出现 401、429、500 或超时。

### 4.5 稳定性测试

用于观察系统在稳定负载下是否持续变慢或出现错误。

建议参数：

| 参数 | 值 |
| --- | ---: |
| 线程数 | 根据阶梯测试结果确定 |
| 目标 RPS | 选择系统可稳定支撑的 RPS |
| 持续时间 | 5-10 分钟 |

### 4.6 读写流程低并发测试

用于验证写入业务链路稳定性和清理能力。

建议参数：

| 参数 | 值 |
| --- | ---: |
| 线程数 | 1 / 3 / 5 |
| Ramp-Up | 5s |
| 循环次数 | 1 / 3 |

要求：

- 每次循环生成唯一测试数据。
- 写入后必须清理。
- 失败时尽量保留响应和错误信息，便于定位。

## 5. 执行顺序

建议按下面顺序推进：

| 阶段 | 内容 | 产物 |
| --- | --- | --- |
| 1 | 整理脚本命名和目录 | 6 个规划 JMX |
| 2 | 执行登录和只读接口基准测试 | debug 报告 |
| 3 | 执行核心只读接口单接口高并发测试 | formal 报告 |
| 4 | 执行只读混合固定 RPS 测试 | formal 报告 |
| 5 | 执行只读混合阶梯 RPS 测试 | formal 报告 |
| 6 | 根据阶梯结果选择稳定负载，执行稳定性测试 | formal 报告 |
| 7 | 补用户、角色菜单、组织架构读写流程低并发测试 | formal 报告 |
| 8 | 汇总关键结果，形成最终性能测试报告 | `performance_report_final.md` |

## 6. 报告目录规范

报告分为三类：

```text
perf_tests/jmeter/reports/
  debug/      # 调试脚本、快速验证生成的临时报告
  formal/     # 正式压测结果报告
  templates/  # 报告模板
```

命名建议：

```text
debug/login_debug.md
formal/read_mix_100rps_30s.md
formal/read_mix_step_10rps.md
formal/read_mix_step_30rps.md
formal/read_mix_step_50rps.md
formal/read_mix_step_100rps.md
formal/performance_report_final.md
```

## 7. 通过标准

当前项目作为本地测试开发项目，建议先采用下面的准入标准：

| 指标 | 标准 |
| --- | --- |
| 错误率 | 0%，最多不超过 1% |
| 查询接口 P95 | 尽量小于 2000ms |
| 登录接口 P95 | 尽量小于 3000ms |
| 固定 RPS 场景 | 实际 Throughput/s 尽量接近目标 RPS |
| 稳定性测试 | 长时间运行错误率不升高，响应时间无持续恶化 |

如果固定 RPS 未达到目标，不直接判定脚本失败，应记录实际吞吐量、响应时间和瓶颈现象。例如：

```text
目标 100 req/s，实际 18.37 req/s，错误率 0%，平均响应 4488ms。
结论：当前本地环境无法支撑 100 req/s，需要降低目标 RPS 或继续分析服务端资源瓶颈。
```
